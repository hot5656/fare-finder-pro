     Admin Dashboard (read-only)

     Context

     There is currently no way to see cross-user data in this app — the
     dashboard only ever reads the signed-in user's own flight.subscriptions row
     (RLS select own). As the app moves toward real usage (ECPay stage
     payments, cron-driven price checks), the operator (you) needs visibility
     into all subscriptions, aggregate status/revenue counts, and notification
     history to sanity-check the system without hand-writing SQL every time.

     The repo has no admin/role concept at all today. Its own backlog
     (docs/m1-session-handoff.md, item B-1, open since 2026-09-20) already flags
     this gap and prescribes the fix: a server-side allowlist table in the
     flight schema, because the existing app_metadata.apps tag (hasAppAccess()
     in src/integrations/supabase/app-scope.ts) is explicitly documented as
     client-declared and non-authoritative — any signed-in user can edit their
     own apps array, so it must never gate real data access, only UI navigation.

     This plan builds a read-only /admin dashboard: full subscriptions list,
     aggregate stats, and notification history, gated by a new flight.admins
     allowlist table enforced through RLS (not a new Edge Function — see
     rationale below). No write/management actions in this pass (confirmed with
     user).

     Approach: RLS-gated reads via a flight.is_admin() helper (not a new Edge 
     Function)

     This repo's established split is: RLS for reads (routes is select true,
     subscriptions is select own), Edge Functions for writes and 
     machine-to-machine calls (flight-subscribe, flight-cancel-subscription,
     plus the service-role-bearer-gated cron/webhook functions). An admin read
     dashboard is a human GET — it fits the RLS side, not the Edge Function
     side. It also means no new deploy is needed for future filter/column
     changes, and no service-role key ever has to reach a browser-facing
     endpoint.

     The blast-radius risk (opening up notification_history, which today has
     zero policies at all) is contained by routing every check through one
     SECURITY DEFINER function, flight.is_admin(), which reads a new
     flight.admins table that itself has no grants/policies for authenticated —
     mirroring how notification_history is locked down today. Even a bug in one
     policy can't accidentally expose data to non-admins, because the single
     source of truth (flight.admins) stays opaque to the client either way.

     1. Migration — 
     supabase/migrations/20260922100000_flight_admin_dashboard.sql

     create table flight.admins (
       user_id uuid primary key references auth.users(id) on delete cascade,
       created_at timestamptz not null default now()
     );
     alter table flight.admins enable row level security;
     -- No policies for authenticated/anon, on purpose — same lockdown as 
     notification_history.
     grant select, insert, update, delete on flight.admins to service_role;

     create or replace function flight.is_admin()
     returns boolean
     language sql stable security definer
     set search_path = flight, pg_temp
     as $$
       select exists (select 1 from flight.admins where user_id = auth.uid());
     $$;
     revoke all on function flight.is_admin() from public;
     grant execute on function flight.is_admin() to authenticated;

     create policy "admins can read all subscriptions"
       on flight.subscriptions for select to authenticated
       using (flight.is_admin());
     -- existing "select own subscriptions" policy stays; policies OR together.

     grant select on flight.notification_history to authenticated;
     create policy "admins can read all notification_history"
       on flight.notification_history for select to authenticated
       using (flight.is_admin());
     -- non-admins: grant lets the query run, RLS returns 0 rows (no matching 
     policy).

     routes needs no change (already select true for authenticated).

     Deploy (per CLAUDE.md — DDL is blocked in auto mode, hand the user this to
     run with !):
     supabase db query --linked --file
     supabase/migrations/20260922100000_flight_admin_dashboard.sql
     supabase migration repair --status applied 20260922100000

     Self-enrollment (by email, avoids a manual UUID lookup):

     Regenerate types (this is how a Lovable "do not edit directly" generated

     src/integrations/supabase/types.ts

     2. Front-end — new route files

     src/routes/_authenticated/admin/route.tsx (new pathless layout nested under
     the existing _authenticated guard):
     - beforeLoad calls supabase.rpc("is_admin"); on error/false, throw 
       redirect({ to: "/dashboard" }) (not /auth — they're a valid signed-in
       user, just not an admin).
     - This check is a UX shortcut only, same category as hasAppAccess() — the
       real boundary is RLS + flight.is_admin(), enforced server-side regardless
       of whether this redirect fires.

     src/routes/_authenticated/admin/index.tsx (/admin, the dashboard page):
     - Three useQuery hooks under fresh query keys (["admin", "subscriptions"],
       ["admin", "routes"], ["admin", "notifications"], distinct from the
       existing ["flight", ...] keys in dashboard.tsx), each a plain
       supabase.from(...).select("*") with no user_id filter — RLS decides what
       comes back, which is also a defense-in-depth check if the route guard is
       ever bypassed.
     - Stat cards (shadcn card.tsx + badge.tsx), derived client-side from the
       fetched arrays: counts per subscription_status, an MRR estimate
       (activeCount * 300 NT$), a payment-failed alert (count of
       payment_failed_at != null, destructive styling when > 0), and a small
       per-route table (last_price, last_price_currency, last_checked_at).
     - Subscriptions table: table.tsx primitives + input.tsx search
       (email/route) + select.tsx or tabs.tsx status filter, combined
       client-side via useMemo — no pagination, no new @tanstack/react-table
       dependency (data scale doesn't need it; table.tsx today is plain
       primitives).
     - Notification history table: notification_history has user_id but no email
       column and no FK PostgREST can auto-embed, so resolve email client-side
       via a Map<user_id, email> built from the already-fetched subscriptions
       array (which denormalizes email); fall back to showing the raw user_id if
       unmatched. Known edge case (acceptable for this MVP pass, leave a // 
       TODO: comment at the lookup site): a user_id with notification history
       but no surviving subscription row (e.g. subscribed, got notified, then
       the row was removed) won't resolve to an email and falls back to the raw
       UUID. If this becomes common, the fix is an admin-only Postgres view
       joining auth.users directly rather than expanding what authenticated can
       read.
     - skeleton.tsx placeholders while the three queries are pending.
     - Optional nicety: a conditionally-shown "Admin" link in dashboard.tsx's
       header via a cached supabase.rpc("is_admin") query — cosmetic only, same
       non-authoritative caveat.

     3. Why this doesn't repeat the app_metadata.apps mistake

     hasAppAccess() / app_metadata.apps is never referenced in the new migration
     or in the admin page's data queries. Admin status is checked in exactly
     two places, both backed by the same flight.is_admin() function: (a) inside
     RLS USING clauses — enforced by Postgres, unbypassable from the client; (b)
     the beforeLoad RPC call — a fast-redirect UX nicety only. A malicious
     app_metadata.apps edit has zero effect on /admin's actual data access.

     Admin Dashboard (read-only)

     Context

     There is currently no way to see cross-user data in this app — the
     dashboard only ever reads the signed-in user's own flight.subscriptions row
     (RLS select own). As the app moves toward real usage (ECPay stage
     payments, cron-driven price checks), the operator (you) needs visibility
     into all subscriptions, aggregate status/revenue counts, and notification
     history to sanity-check the system without hand-writing SQL every time.

     The repo has no admin/role concept at all today. Its own backlog
     (docs/m1-session-handoff.md, item B-1, open since 2026-09-20) already flags
     this gap and prescribes the fix: a server-side allowlist table in the
     flight schema, because the existing app_metadata.apps tag (hasAppAccess()
     in src/integrations/supabase/app-scope.ts) is explicitly documented as
     client-declared and non-authoritative — any signed-in user can edit their
     own apps array, so it must never gate real data access, only UI navigation.

     This plan builds a read-only /admin dashboard: full subscriptions list,
     aggregate stats, and notification history, gated by a new flight.admins
     allowlist table enforced through RLS (not a new Edge Function — see
     rationale below). No write/management actions in this pass (confirmed with
     user).

     Approach: RLS-gated reads via a flight.is_admin() helper (not a new Edge 
     Function)

     This repo's established split is: RLS for reads (routes is select true,
     subscriptions is select own), Edge Functions for writes and 
     machine-to-machine calls (flight-subscribe, flight-cancel-subscription,
     plus the service-role-bearer-gated cron/webhook functions). An admin read
     dashboard is a human GET — it fits the RLS side, not the Edge Function
     side. It also means no new deploy is needed for future filter/column
     changes, and no service-role key ever has to reach a browser-facing
     endpoint.

     The blast-radius risk (opening up notification_history, which today has
     zero policies at all) is contained by routing every check through one
     SECURITY DEFINER function, flight.is_admin(), which reads a new
     flight.admins table that itself has no grants/policies for authenticated —
     mirroring how notification_history is locked down today. Even a bug in one
     policy can't accidentally expose data to non-admins, because the single
     source of truth (flight.admins) stays opaque to the client either way.

     1. Migration — 
     supabase/migrations/20260922100000_flight_admin_dashboard.sql

     create table flight.admins (
       user_id uuid primary key references auth.users(id) on delete cascade,
       created_at timestamptz not null default now()
     );
     alter table flight.admins enable row level security;
     -- No policies for authenticated/anon, on purpose — same lockdown as 
     notification_history.
     grant select, insert, update, delete on flight.admins to service_role;

     create or replace function flight.is_admin()
     returns boolean
     language sql stable security definer
     set search_path = flight, pg_temp
     as $$
       select exists (select 1 from flight.admins where user_id = auth.uid());
     $$;
     revoke all on function flight.is_admin() from public;
     grant execute on function flight.is_admin() to authenticated;

     create policy "admins can read all subscriptions"
       on flight.subscriptions for select to authenticated
       using (flight.is_admin());
     -- existing "select own subscriptions" policy stays; policies OR together.

     grant select on flight.notification_history to authenticated;
     create policy "admins can read all notification_history"
       on flight.notification_history for select to authenticated
       using (flight.is_admin());
     -- non-admins: grant lets the query run, RLS returns 0 rows (no matching 
     policy).

     routes needs no change (already select true for authenticated).

     Context

     The admin dashboard (/admin, shipped in commit 303d277) currently only
     reads data. flight-notification's dedup rule (shouldSend in
     supabase/functions/flight-notification/index.ts) skips a repeat email if
     the last one for that (user_id, route) was sent under 24h ago at a similar
     price — correct for the automatic cron path, but it means the admin can't
     force a re-send to a specific subscriber even when their target price
     currently matches the last known fare, e.g. for support requests ("I never
     got the email") or manual QA. This plan adds a per-subscription "manually
     send" action to /admin that bypasses the dedup floor for one explicit,
     admin-authorized send.

     Confirmed with user: single-subscription trigger (not per-route bulk),
     reuse the already-cached flight.routes.last_price (no live Travelpayouts
     re-fetch), and record which admin triggered each manual send for audit
     purposes. Also confirmed and re-affirmed: (1) after regenerating types.ts,
     the DefaultSchema line must be re-patched from "public" to Extract<keyof 
     Database, "flight"> (same CLI-version quirk hit last time); (2) the
     booking-link trade-off in step 3 (empty depart_date -> generic
     origin/destination search link, no dated link) is accepted as-is for this

     Design

     Data flow: admin clicks "手動發送" on a matching subscription row → browser
     calls a new Edge Function flight-admin-notify with the user's own JWT →
     that function verifies the caller is a real admin (via flight.admins, same

     subscription is currently paying and matching, builds a Match object from
     the subscription + flight.routes.last_price, and internally POSTs it to the
     existing flight-notification with a new force: true flag (service-role
     bearer, same internal-call pattern flight-parser already uses) so
     shouldSend's dedup check is bypassed for this one send. flight-notification
     keeps being the single place that renders the email, calls Resend, and
     writes notification_history — nothing about its normal automatic path
     changes when force is absent/false.

     Function (never a direct client insert — notification_history still has no

     JWT-verification shape already used by flight-cancel-subscription
     (supabase/functions/flight-cancel-subscription/index.ts):

     Admin: manually trigger a price-drop notification

     Context

     The admin dashboard (/admin, shipped in commit 303d277) currently only
     reads data. flight-notification's dedup rule (shouldSend in
     supabase/functions/flight-notification/index.ts) skips a repeat email if
     the last one for that (user_id, route) was sent under 24h ago at a similar
     price — correct for the automatic cron path, but it means the admin can't
     force a re-send to a specific subscriber even when their target price
     currently matches the last known fare, e.g. for support requests ("I never
     got the email") or manual QA. This plan adds a per-subscription "manually
     send" action to /admin that bypasses the dedup floor for one explicit,
     admin-authorized send.

     Confirmed with user: single-subscription trigger (not per-route bulk),
     reuse the already-cached flight.routes.last_price (no live Travelpayouts
     re-fetch), and record which admin triggered each manual send for audit
     purposes. Also confirmed and re-affirmed: (1) after regenerating types.ts,
     the DefaultSchema line must be re-patched from "public" to Extract<keyof 
     Database, "flight"> (same CLI-version quirk hit last time); (2) the
     booking-link trade-off in step 3 (empty depart_date -> generic
     origin/destination search link, no dated link) is accepted as-is for this
     pass.

     Design

     Data flow: admin clicks "手動發送" on a matching subscription row → browser
     calls a new Edge Function flight-admin-notify with the user's own JWT →
     that function verifies the caller is a real admin (via flight.admins, same
     table the dashboard already uses), re-validates server-side that the
     subscription is currently paying and matching, builds a Match object from
     the subscription + flight.routes.last_price, and internally POSTs it to the
     existing flight-notification with a new force: true flag (service-role
     bearer, same internal-call pattern flight-parser already uses) so
     shouldSend's dedup check is bypassed for this one send. flight-notification
     keeps being the single place that renders the email, calls Resend, and
     writes notification_history — nothing about its normal automatic path
     changes when force is absent/false.

     This mirrors the codebase's existing split: a write goes through an Edge
     Function (never a direct client insert — notification_history still has no
     authenticated INSERT policy), and the new function follows the exact
     JWT-verification shape already used by flight-cancel-subscription
     (supabase/functions/flight-cancel-subscription/index.ts):
     admin.auth.getUser(jwt) to get a trustworthy user.id, never trusting the
     request body for identity.

     Context

     Testing the admin manual-notify feature (just shipped) surfaced a gap in
     the notification email itself, not specific to manual sends: the email
     shows a price ("NT$6,610 / 約 US$208") but never says which flight that
     price is for. The Cheapest type already carries airline and depart_date

     airline is currently hardcoded to "" because -- unlike
