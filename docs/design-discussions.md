## D-1 查價條件與「未來 60 天滾動查詢」

- **日期**：2026-09-27
- **狀態**：評估中（評估完成、尚未實作，實作前待確認事項見 3.6）
- **摘要**：目前只查「下個月整月」的來回最低價。建議改成未來 60 天滾動查詢；API 呼叫數每條航線最多從 2 次變 4 次，以目前航線數沒有影響。
- **相關手冊**：[`travelpayouts-limits-and-monitoring.md`](travelpayouts-limits-and-monitoring.md)（API 限額、容量估算）

### 1. 目前的查價條件

`flight-parser` 每 30 分鐘執行一次，查詢邏輯在 `supabase/functions/_shared/travelpayouts.ts`：

| 條件 | 設定 | 說明 |
| --- | --- | --- |
| 出發日期 | `nextMonth()`：依 UTC 計算的**下一個月整個月** | 例如 2026-09-27 查 2026-10 整月任何一天出發；到 10/1 就改查 11 月。不是「30 天內」，也不是「所有已公告的票」 |
| 行程 | `one_way=false` | 來回票 |
| 回程日期 | 不指定 | 任何回程日都可以，停留天數不固定 |
| 轉機 | 不限（沒有帶 `direct`） | 含轉機的票 |
| 排序／筆數 | `sorting=price`、`limit=5` | 取最便宜的 5 筆，再挑出最低價 |
| 幣別 | TWD 用來觸發通知；USD 只顯示 | USD 另外查一次（見第 2 節） |

v3 `aviasales/v3/prices_for_dates` 用來觸發通知；v1 `prices/cheap` 只放在通知信裡當對照，admin 可以關閉。`flight-admin-routes` 新增航線時的「查得到價格才可新增」也是用同一個條件（下個月）。

#### 資料來源的性質

Travelpayouts Data API 回傳的是**快取價格**，來自其他使用者最近在 Aviasales 的搜尋紀錄，不是即時報價，也不是航空公司公告的全部票價。熱門航線（東京、首爾）資料比較完整，冷門航線或冷門月份可能查不到（`no_fare`），信裡的價格和實際訂票時的價格也可能不一樣。

#### 目前做法的問題

1. **換月時價格會跳動**：每月 1 號查詢範圍直接換到新的月份，最低價可能突然變化，觸發通知或讓原本的低價消失。
2. **查得到的最近日期會隨月份進度變化**：9/1 查的是 30～60 天後出發的票，9/27 查的卻是 4～34 天後出發的票。
3. 使用者**不能選出發日、停留天數或是否直飛**，通知的最低價可能是轉機票，或停留天數不適合使用者。

### 2. 為什麼每條航線要打 2 次 API

v1 對照關閉時，每條航線用兩種幣別各查一次 v3，都查下個月（`flight-parser/index.ts`）：

```ts
fetchCheapestV3(origin, destination, month, "TWD")   // 第 1 次：判斷要不要發通知
fetchCheapestV3(origin, destination, month, "USD")   // 第 2 次：顯示在旁邊的約當美金
```

Travelpayouts 依 `currency` 參數決定回傳的幣別，程式裡沒有自己換算匯率，所以美金要另外查。v1 對照開啟時，再加上 v1 的 TWD 和 USD 兩次，總共 4 次。

如果美金改成用 TWD 價格乘上匯率換算，就可以省掉 USD 那一次。不過換算出來的價格和 Travelpayouts 回傳的美金票價可能有差異。

### 3. 評估：改成未來 60 天滾動查詢

結論：**可行，而且建議做**。要改的東西不多，代價是每條航線的 API 呼叫數最多變成 2 倍，以目前的航線數量沒有影響。

#### 3.1 做法

v3 的 `departure_at` 只能填**一個月份（`YYYY-MM`）或一天**，沒有日期區間參數，所以要這樣組出 60 天的查詢：

1. 算出查詢區間：預設從**明天到第 60 天**，以台北時間計算（起始日要不要延後見 3.6）。
2. 找出區間涵蓋的月份。例如 9/27 的區間是 9/28～11/26，涵蓋 9、10、11 月三個月；每月 1 號的區間通常只涵蓋 2 個月。
3. 每個月各查一次 v3 TWD（平行發出），把 `departure_at` 不在區間內的票濾掉，再取最低價。`departure_at` 帶有出發地的 UTC 時差，要用日期部分比對。
4. `limit` 從 5 提高到約 100。頭尾兩個月只有部分日期在區間內，最便宜的前 5 筆可能全部落在區間外，濾掉後就沒有票了。
5. USD 和 v1 只是參考，**只查 TWD 最低價所在的那個月**。

#### 3.2 API 用量

| | 目前（下個月） | 60 天滾動 |
| --- | --- | --- |
| 每條航線，v1 關閉 | 2 次 | 最多 4 次（TWD 3 個月＋USD 1 個月；每月 1 號約 3 次） |
| 每條航線，v1 開啟 | 4 次 | 最多 6 次 |
| 目前 4 條航線、v1 關閉，每次執行 | 8 次 | 最多 16 次 |
| 執行時間 | 約 4～5 秒 | 差不多。TWD 平行查，USD 要等 TWD 結果，所以每條航線多一輪請求，約多 0.5～1 秒 |

`travelpayouts-limits-and-monitoring.md` 第 2 節的容量表要重算。假設 v3 的實際上限是 100 RPM（這個數字還沒確認），開始碰到 429 的航線數會從**約 50 條降到約 25 條**（v1 關閉的情況）。目前只有 4 條航線，離上限還很遠。

#### 3.3 對使用者的影響

好處：

- **換月時價格不會突然跳動**：區間每天往後移一天，價格只會隨著日期進出區間慢慢變化。
- **`no_fare` 會變少**：日期範圍變大，冷門航線比較容易查到價格。
- **一定查得到近期出發的票**：不會再有月底時只查得到 30 天以後出發的情況。

要注意：

- **上線時可能一次寄出一批通知**：60 天內的最低價一定不會比單一月份高。目標價剛好落在舊價和新價之間的訂閱者，第一輪就會收到通知。這符合產品邏輯，但要先知道會發生。dedup（24 小時內同價格不重複發）照常運作。
- **近期出發的快取價格比較不可靠**：例如明天出發的票，使用者點進去常常已經訂不到或已經漲價。
- dashboard 的 `last_price` 在上線後會整體往下調整一次。

#### 3.4 要改的檔案

| 檔案 | 改什麼 |
| --- | --- |
| `supabase/functions/_shared/travelpayouts.ts` | 新增區間查詢函式，取代 `nextMonth()` 和單月份查詢 |
| `supabase/functions/flight-parser/index.ts` | 改用新函式；log 和 `no_fare` 訊息改成顯示區間，不再顯示月份 |
| `supabase/functions/flight-admin-routes/index.ts` | 預覽和新增時的驗證改用同一個區間，否則「查得到才可新增」會和實際查價不一致；回傳的 `month` 改成區間 |
| `src/routes/_authenticated/admin/routes.tsx` | 「系統會即時查詢下個月的來回最低票價」和 `{preview.month}` 改成顯示區間 |
| 文件 | `travelpayouts-limits-and-monitoring.md`（用量與容量表）、`test-plan.md` AD-06、`ppt-outline_1.1_system.md`，以及本議題的狀態 |

通知信本來就會列出實際的去回程日期，不用改。改完要重新部署 `flight-parser` 和 `flight-admin-routes`。

#### 3.5 其他做法（沒有採用）

- **查下兩個月整月**：每條航線要多打 1 次 v3 TWD，但換月時還是會跳動，只是把問題延後一個月。
- **用 TWD 換算美金、不查 USD**：可以省掉 1 次呼叫，但換算價格和 Travelpayouts 的美金票價可能不同。可以另外評估，和 60 天滾動查詢沒有關係。

#### 3.6 實作前待確認

1. **v3 單月查詢一次能拿到多少筆**：要確認 `departure_at=YYYY-MM`、`limit=100` 時，是否真的回傳整個月的多筆資料，而不是每個出發日只回傳一筆。這會影響 3.1 第 4 步的過濾方式。Token 只存在 Edge secret，需要在本機設定 `TRAVELPAYOUTS_TOKEN` 後自己跑：

   ```sh
   curl -s "https://api.travelpayouts.com/aviasales/v3/prices_for_dates?origin=TPE&destination=TYO&departure_at=2026-11&one_way=false&sorting=price&limit=100&currency=TWD&token=$TRAVELPAYOUTS_TOKEN" \
     | jq '{n: (.data|length), dates: [.data[].departure_at[0:10]] | unique | length}'
   ```

2. **區間起始日**：建議從**第 3 天**開始，避開不可靠的近期快取價格；也可以照字面從明天開始。
