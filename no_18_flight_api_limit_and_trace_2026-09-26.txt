⏺ 有限制，但以這個專案目前的用量，離上限還很遠。

  官方的限制

  - 從 2024-06-14 起，Travelpayouts
    的限額改成以「每分鐘請求數（RPM）」計算，以前是每 5 分鐘和每小時。每個
    endpoint 的上限不一樣，例如 Data API 的 /v1/prices/calendar 是 300
    RPM，/statistics/v1/execute_query 是 30 RPM。
  - 超過上限會回 HTTP 429。
  - 即時搜尋的 Flights Search API 限得比較嚴，同一個 IP 每小時約 100～200
    次。我們沒有用這支。

  我們實際用到的 aviasales/v3/prices_for_dates、v1/prices/cheap、autocomplete.tr
  avelpayouts.com/places2，確切的 RPM 我沒查到。官方的限額頁面擋在 Cloudflare
  驗證後面，我抓不到內容，所以不亂寫數字。要確認可以直接到限額頁面看，或登入
  Travelpayouts 後台查。

  專案的用量（依 supabase/functions/flight-parser/index.ts:161-187）

  - 每 30 分鐘跑一次，每條航線最多打 4 次：v3 的 TWD 和 USD
    各一次；比較區塊開著的話，v1 的 TWD 和 USD 再各一次。
  - 航線是一條一條處理，所以同時最多只有 4 個請求。
  - 以目前 3 條航線算，每次跑約 12 次，換算下來不到 1
    RPM。就算加到幾十條航線，也還在一般 Data API 的上限內。
  - 另外，管理員在 /admin/routes 預覽或建立航線時，會打 places2 和 v3
    各一兩次，量很小。

  比次數更需要注意的限制

  - Data API 給的是快取價格，來自其他使用者最近的搜尋紀錄，不是即時報價。冷門航
    線或冷門月份可能查不到價格，這也是建立航線時要求「v3
    查得到價格才存」的原因。通知信裡的價格跟使用者點進去看到的，也可能有差距。
  - 這是聯盟行銷（affiliate）用的 API，使用條款要求導流連結帶上 marker。這部分
    flight-notification 已經處理了（withMarker）。
  - 如果之後遇到 429，目前的 safe() 只會把該航線這一輪跳過，下一輪 30
    分鐘後再重試，不會讓整批失敗。

  Sources:
  - API rate limits – Travelpayouts Help Center
  - What are the restrictions on API requests? – Travelpayouts Help Center
  - Aviasales Data API – Travelpayouts Help Center
  - Aviasales Flights Search API – Travelpayouts Help Center

⏺ 簡短的答案：以現在的寫法，Travelpayouts 
  的限額應該不會是最先碰到的上限。航線加到大約 100～150 條時，Edge Function 
  的執行時間上限會先卡住。 不過 v3 的官方 RPM 我沒查到（官方限額頁面擋在
  Cloudflare 後面），所以下面的門檻是推算，不是保證。

  實測數據（今天的 log）
  - 目前有 4 條航線，全部啟用；v1 比較是關著的，所以每條航線打 2 次（v3 TWD、v3
    USD）。
  - 每次 flight-parser 執行約 4.4～5 秒，偶爾到 7 秒，全部回
    200。這個時間包含到期處理和資料庫操作。以此粗估，每條航線約 1 秒。

  關鍵：限額看的是「每分鐘打幾次」，不是「總共打幾次」
  - 航線是一條一條處理的，同時只有 2 個請求（v1 打開時是 4
    個）。所以一分鐘內能打的次數有天花板：大約 60 條航線 × 2 ≈ 120 RPM，v1
    打開時約 240 RPM。
  - 航線超過約 60 條以後，不會打得更快，只是整次執行拉得更長，RPM
    會停在上面這個數字。

  什麼程度可能被 429

  ┌─────────────────────────────────────────────┬──────────┬──────────┐
  │           v3 的實際上限（未確認）           │  v1 關   │  v1 開   │
  ├─────────────────────────────────────────────┼──────────┼──────────┤
  │ ≥ 300 RPM（跟 Data API 其他 endpoint 同級） │ 不會碰到 │ 不會碰到 │
  ├─────────────────────────────────────────────┼──────────┼──────────┤
  │ 約 100 RPM                                  │ 約 50 條 │ 約 25 條 │
  ├─────────────────────────────────────────────┼──────────┼──────────┤
  │ 約 60 RPM                                   │ 約 30 條 │ 約 15 條 │
  └─────────────────────────────────────────────┴──────────┴──────────┘

  比較可能先碰到的上限
  1. Edge Function 的執行時間上限。 Supabase 的上限是 150 秒（Free）或 400
     秒（Paid）。以每條約 1 秒算，大約 150 條（Free）或 400 條（Paid）
     會超時，後面的航線那一輪就查不到價格。
  2. Data API 本身的資料覆蓋率。
     冷門航線可能常常沒有快取價格。這不是被限制，但加再多航線也沒用。

  建議
  - 航線到幾十條時，看 log 有沒有 429 或 skip …: no v3 TWD fare。遇到 429 時
    safe() 只會跳過那條航線，所以問題會「靜靜地」出現，不會報錯。
  - 真的要擴到上百條時，再做兩件事：航線之間加一點延遲或限制併發，把 RPM
    壓在確定安全的值；再把工作拆成多批，例如每次只跑一部分航線，或分成多個 cron
    排程，避開執行時間上限。
  - 最準的做法是直接問 Travelpayouts 支援，或登入後台看
    aviasales/v3/prices_for_dates 的確切 RPM。

  現在 4 條航線、每 30 分鐘只打 8 次，離任何上限都很遠。

  - Overview (/admin): a status banner at the top. Green means the last price

    - a failed USD or v1 fetch;

  How it works
  - New table flight.parser_runs: each run is inserted as running when it starts
    and filled in when it finishes. Only admins can read it; only the service
    role can write to it. Rows are kept for 90 days, about 48 a day.

    now raises a FareHttpError that carries the status code, so a 429 can be
    told apart from a route that simply has no fare.

      any failure as "no fare".

    route with no fare. Writing the record is best-effort: if it fails, the

  1. Travelpayouts limits: rate limits are counted per minute and going over
     returns 429. It lists the three endpoints the project uses and which

     for the v3 endpoint, and the doc says so and explains how to find out. It
     also covers the two limits that matter more than call counts: prices are
     cached (not live), and booking links must carry the affiliate marker.
  2. Usage and capacity estimates:
     - Measured today: 8 calls per run, about 4–5 seconds.
     - Because routes are checked one at a time, the request rate stops rising
       at about 120 per minute (v1 comparison off) or 240 (on).
     - A table estimates how many routes it takes to start getting 429s,
       depending on what the real limit turns out to be.
     - The more likely ceiling is the 150-second time limit, at around 150
       routes.
     - It lists what to do before growing to hundreds of routes.
  3. What each run records: what each column in flight.parser_runs means. For
     example, "routes checked" includes routes that returned no fare, and
     "matches" is not the number of emails actually sent.
  4. How to analyze the Price checks page:
     - Step 1, the banner: what each red, yellow and green message means.
     - Step 2, a single run: how ok, warning and error are decided, and a table
       of the 5 problem types with their effect and what to do.
     - Step 3, trends: four read-only SQL queries: status counts over 7 days,
       which routes have problems most often, daily duration and API calls, and
       gaps in the schedule.
     - Common cases: London showing no fare every run, 429s on several routes at
       once, 401/403 on every route, run time creeping up, and the schedule
       stopping.

     recorded here, and nothing notifies the admin; they have to open the admin
